# レシピ取得方針

関連タスク: Issue #7（Supabase backend実装）/ #8（レシピ初期データseed）/ #9（Supabase日本語全文検索）/ #11（食材マッチングスコアリング）/ #12（お好み設定フィルタリング）/ #13（DBヒット不足時のAIアレンジ補完）

## 検討した選択肢と判断

| 方式 | 判断 | 理由 |
|------|------|------|
| 既存レシピをAPIで取得 | ❌ 不採用 | 著作権・利用規約リスクが大きい。合法的に食材ベースで検索できるレシピAPIがほぼ存在しない |
| 楽天レシピAPI | ❌ 不採用 | カテゴリ検索のみで食材ベースの検索不可、1カテゴリ上位4件のみ、商用利用禁止、APIバージョンが2017年で停止 |
| ユーザー投稿型 | ❌ 不採用 | コールドスタート問題。レシピが集まるまでアプリが機能しない。4人チームでは非現実的 |
| AIにレシピを完全生成 | ❌ 不採用（初期案） | 著作権リスクはゼロだが、レシピの品質・再現性が不安定になりやすいと判断し方針転換 |
| **自作レシピDB（seed）＋検索スコアリング＋AIアレンジ補完** | ✅ 採用（現行方式） | 著作権リスクなし（自作データ）。DB検索で再現性のあるレシピを優先しつつ、DBの手持ちが少ない場合のみAIが補完してカバレッジを確保する |

## 現行方式の仕組み

1. `backend/db/seed/recipes.json` に手動作成したレシピを投入する（目標50件以上。Issue #8）
2. Supabase (PostgreSQL) の全文検索（pg_bigm / pgroonga）で食材名から日本語レシピを検索できるようにする（Issue #9）
3. 入力食材と各レシピの `recipe_ingredients` を突き合わせ、一致数でスコアリングし上位5件を返す。「手持ちのみモード」では `is_optional=false` の必須食材が揃っているレシピのみに絞る（Issue #11, `backend/services/recipe_search.py`）
4. お好み設定（ジャンル・調理法・味・ボリューム）が「おまかせ」でない場合のみ、動的にWHERE句を組み立ててフィルタリングする（Issue #12）
5. DB検索結果が3件未満の場合、近いレシピを出典としてGemini APIに渡し「〇〇をベースにアレンジ」の形式で補完提案させる（Issue #13, `backend/services/recipe_arrange.py`）
6. レスポンスの `source` フィールドに `"db"` または `"ai_arrange"` を付与し、フロント側で出典を明示できるようにする

## 注意点

- レシピの正確性は保証されないため「AIが提案したレシピです」と明示する（特にAIアレンジ提案時）
- 開発中はGemini API（無料枠）で開発コストを抑える
